## 1. Gesamturteil

Ungewöhnlich saubere Codebase. Die Kernideen tragen:

- **Modulith-Grenzen** werden per Test erzwungen (`ModulstrukturTest`), der Event-Vertrag ist
  zweistufig sauber getrennt (Aggregat-`SpielEreignis` → Modul-Events `partie.ereignisse` → WS-DTOs).
- **Snapshot+Hint** mit `@Version` als einziger Sequenznummer ist elegant und hält das Frontend
  wirklich „dumm"; Self-Healing über Batch-Lücken-Erkennung funktioniert wie spezifiziert.
- **DB als einzige Wahrheit** wird konsequent durchgehalten — gezielt gesucht: keine Registry,
  kein In-Memory-Lock, kein `isNew`-Hack.
- **Listener-Disziplin** sauber: alle Seiteneffekt-Listener `@TransactionalEventListener(AFTER_COMMIT)`
  bzw. `@ApplicationModuleListener`; die zwei nackten `@EventListener` betreffen nur
  WS-Session-Infrastruktur (legitim). Pattern A ohne `@DomainEvents` eingehalten.
- **Fachliche Regel-Specs stimmen mit dem Code überein** — stichprobenhaft verifiziert: zweite
  Dulle (`NormaleTrumpfOrdnung`), Gegen-die-Alten (`PunkteRechner`), Solo-Multiplikator
  (Archiv-Spalte), Schmeißen-Varianten, 800ms-KI-Delay exklusiv im FE (`StoreTypen.ts:79`).
- **Datenbankschema** deckt sich vollständig mit `datenbankmodell.md` inkl. aller
  REFACTOR-DB-Nachträge (partielle UNIQUE-Indizes, PK auf `event_publication`, FK-Indizes aus
  `002-schema-fixes.sql`). Biome-Schwelle steht real auf 15.

**Hauptproblem ist nicht der Code, sondern Spec-Drift** — konzentriert auf die *technischen
Referenz-Specs*, die Code-Strukturen duplizieren (Event-Tabellen, DTO-Definitionen, Datei-Listen,
Endpunkt-Listen). Details in Abschnitt 2; strukturelle Ursache und Gegenmittel in Abschnitt 3.

## 2. Spec-vs-Code-Abweichungen (Befunde)

### 2.1 `architektur-domain-events.md` — Event-Tabelle beschreibt Events, die es nicht gibt

- `AnsageErwartet` wird als Domain-Event mit Listener `KiTischOrchestrator.onAnsageErwartet()`
  gelistet — **existiert nirgends im Code** (weder Klasse noch Record).
- `HochzeitPartnerGefunden` wird als Modul-Event in `partie.ereignisse` geführt — existiert nur
  als Aggregat-Ereignis `SpielEreignis.HochzeitPartnerGefunden` (`SpielEreignis.java:27`).
  Die Tabelle vermischt die zwei Event-Ebenen, die die Spec selbst definiert.
- Namenskonvention laut Spec `onXyz()` — Code nutzt durchgängig `beiXyz()`
  (`KiTischOrchestrator.java:79ff`). Der Orchestrator lauscht zusätzlich auf
  `KiUebernahmeEreignis`, das in keiner Spec-Tabelle auftaucht.
- „SchweinchenGemeldet — V1: kein WS" ist überholt: `SCHWEINCHEN_GEMELDET` ist WS-Typ
  (`PartieEreignisTyp.java:23`); `ANSAGE_ERFOLGT` fehlt in der WS-Tabelle komplett.
- `PartieEreignisBatch` mit optionalem `snapshot?:`-Feld dokumentiert — der Code-Record hat nur
  `version` + `ereignisse` (`PartieEreignisBatch.java:14`).
- Das Sequenzdiagramm beschreibt noch das alte rekursive KI-Modell (Event → einzelner KI-Zug →
  Event); real läuft eine synchrone Schleife in `KiTischOrchestrator.automatisiereTisch`
  (`REQUIRES_NEW`, ein Batch pro Commit).

→ Task **DOC-SPEC-EVENTS-SYNC** (inkl. Event-Tabelle in `architektur.md`: 5 von 9 Klassen gelistet).

## 3. Architektur-Diskussion

**Strukturelle Wurzelursache der Drift:** 56 Specs, davon ein Teil mit maschinenprüfbarem
Code-Wissen (Event-Namen, DTO-Felder, Endpunkte, Dateilisten). Jedes Refactoring erzeugt genau
dort Pflege-Schulden. Empfehlung: Specs in **„Regeln & Warum"** (stabil, handgepflegt) und
**„Referenz"** (aus Code ableitbar) trennen. `check_specs.py` ist der perfekte Ansatzpunkt für
einen **Spec-Lint**, der aus Specs referenzierte Klassennamen/Enum-Werte/Destinations gegen
`src/` + `frontend/src/` grept — hätte jede der obigen Abweichungen automatisch gemeldet.
→ Task **QA-SPEC-LINT**.

**Bewusste Trade-offs, die okay sind (aber dokumentiert gehören):**
- `KiTischOrchestrator`-Schleife: synchron in einer `REQUIRES_NEW`-Transaktion — Einfachheit
  gegen längere TX; Broadcast erst AFTER_COMMIT, FE glättet mit 800ms-Queue-Delay. Gut so.
- `PartieStandAntwort` (529 Z.) ist der Preis des Snapshot-in-Event-Modells.

**Radar (kein Handlungsdruck):**
- Klassengrößen vs. Richtwert 300: `Spiel` (542) / `Partie` (471) als Aggregate verteidigbar;
  `StandardKiStrategie` (504) und `TischVerwaltungsService` (465) wären nach dem geplanten
  `JsonbConverter`-Refactoring (915) die nächsten echten Kandidaten.
- `AppStore.snapshot()` macht `structuredClone` des Gesamtzustands pro Listener-Benachrichtigung —
  bei Spielgröße unkritisch; wird der erste FE-Hotspot, falls Protokoll/Historie im Zustand wächst.

## 4. Ralph-Review (`ralph.sh`, `PROMPT_build.md`, `PROMPT_plan.md`)

Deutlich reifer als typische Ralph-Loops (Vor-Validierung mit Pflicht-`clean`, Subagenten-Split
Spec/Code, Vision-Loop-Gate, Plan-Update vor Commit, 3-Versuche-Stoppregel, Rate-Limit-Retry mit
Iterations-Gutschrift). Echte Schwächen:

1. **COMPLETE kann strukturell nie feuern:** `grep -c '^\- \[ \]' IMPLEMENTATION_PLAN.md` zählt
   auch Block B (MENSCH), C (User-Entscheidung), D (Zurückgestellt) — dort stehen dauerhaft
   offene `- [ ]`. Folge: nach dem letzten autonomen Task läuft jede Folge-Iteration inkl.
   voller Vor-Validierung, bis das Iterationslimit greift. **Fix:** Zählung auf Sektion A
   begrenzen (`sed -n '/^## A)/,/^## B)/p' … | grep -c …`).
2. **Vier konkurrierende „Empfohlene Build-Reihenfolge"-Sektionen** (S142/145/146/147) bei
   gleichzeitigem „folge ihr strikt". **Fix:** genau eine Sektion; Plan-Modus konsolidiert alte.
3. **Prefix-Validierungs-Mapping unvollständig:** Plan nutzt `SCHEMA-`, `SECURITY-`, `QA-`,
   `DEPS-`, `CLEANUP-`, `TEST-`, `OPS-` — Build-Prompt kennt dafür keine Validierung; Plan-Prompt
   listet nur 5 Prefixe. **Fix:** Fallback-Regel („`git status -s` entscheidet") + Listen syncen.
4. **Kein Timeout um den `claude`-Aufruf** — ein hängender CLI-Prozess blockiert die Loop
   unbegrenzt. **Fix:** `timeout`-Wrapper (Env-Override).

Kleinere Punkte: auskommentierter Dirty-Worktree-Check (uncommitted Plan-Änderungen wandern
still in den nächsten Task-Commit); COMPLETE-Erkennung grept rohes stream-json (Chunk-Split
möglich); Rate-Limit-Feldnamen gegen CLI-Version verifizieren; Ralph-Logs liegen neben
`logs/locodoko.log` (Debugging-grep-Kollision) → `logs/ralph/`; Modell-Kommentare veraltet
(`claude-opus-4-6` → aktuell `claude-opus-4-8`); `MAX_ITERATIONS=0` = endlos undokumentiert;
0e „Maximal 10 Tool-Calls (… eher mehr nutzen)" widersprüchlich; git-add-Hinweis mit doppelter
Verneinung; `PROMPT_plan.md` „Erledigte Einträge behalten" widerspricht gelebter Archiv-Praxis;
Plan-Modus pflegt Spec-Status-Zeilen nicht explizit (der `bugreport.md`-„Entwurf"-Fall).
